# LLM1 분류 기준

확정: 2026-10-21, 사용자 합의. 현재 목업 기반 기능 검증의 분류 기준은 이 문서로 고정합니다. 변경은 사용자와 다시 합의하며, 후속 보강 항목을 현재 필수 조건으로 추가하지 않습니다. 팀 코드 검토 후 사용자 지시로 LLM1과 FastAPI 서버를 구현했습니다.

## 현재 목적과 기준 데이터

사용자 결정에 따라 현재 Backend 목업과 테스트 시나리오를 서비스 흐름 검증의 기준으로 사용합니다. 이 데이터 양식에서 확인 가능한 정보로 이력 연결과 담당 부서 제안을 판단합니다. 더 엄격한 항공 정비 기준, 상세 위치·발생 조건의 일치 기준, 운영 성능 검증은 후속 프로젝트에서 보강합니다.

초기 참조 버전은 Backend `5cb02b8705290826a12764edc772b01f5881d5bc`입니다. 최신 `640b960502db1cfd3d3ad0d1d93259efec51b366`에는 FCS(ATA 27), 이력 78건, S23이 추가됐습니다. 현재 데이터는 1,577건·8개 부서·AI 시나리오 23건과 접수 검증 6건입니다. 아래 기존 링크·수치는 초기 기준이며 충분성 원칙은 그대로 유지합니다.

- [정비 이력 시드](https://github.com/mro-agent-proj/backend/blob/5cb02b8705290826a12764edc772b01f5881d5bc/seed/maintenance_history.csv): 1,499건. `id`, `tail_number`, `reported_at`, `symptom_text`, `ata_chapter`, `jasc_code`, `action_taken`, `department_code`, `closed_at`.
- [부서 시드](https://github.com/mro-agent-proj/backend/blob/5cb02b8705290826a12764edc772b01f5881d5bc/seed/departments.csv): 7개 부서와 담당 ATA.
- [시나리오](https://github.com/mro-agent-proj/backend/blob/5cb02b8705290826a12764edc772b01f5881d5bc/seed/scenarios.md): AI 경로 S01~S22와 Backend 접수 검증 V1~V6. 시연 기준일은 2026-10-21.

발생 단계·고도·온도·부위·위치는 별도 컬럼이 아니라 증상 문장에 일부 포함됩니다. 원본 SDR 행을 가리키는 ID는 이 시드에 없습니다. 실시간 판단 근거는 business-mcp가 반환한 요청·기체 이력·부서 정보이며, 시나리오 문서의 정답을 모델 입력으로 제공하지 않습니다.

## 사용자와 합의한 기본 방향

**같은 기체의 증상·발생 조건과 담당 부서 연결 근거가 충분하면, LLM2 추가 조사 없이 담당 부서 배정을 제안할 수 있습니다.**

현 단계에서 충분성은 목업이 제공하는 정보 수준으로 판단합니다. 표현·세부 위치·발생 조건이 완전히 같아야 한다는 조건은 두지 않습니다. 조건이 누락되거나 일부 달라도, 관찰된 증상과 대상 계통·부품 및 과거 담당 부서가 현재 부서 담당 범위로 연결되면 허용합니다. 확인되지 않은 조건을 같다고 추정해 채우지는 않습니다.

과거 조치 내용과 그 결과의 확인은 모든 부서 제안의 필수 조건이 아닙니다. 제공된 조치·결과는 대상 계통과 부서 연결을 설명하는 보강 정보로 사용합니다. 충분성은 담당 부서를 제안할 근거에 대한 판단이며 정비 방법이나 운항 가능 여부를 결정하지 않습니다.

## 확정한 판단 기준

| 항목 | 현재 적용할 기준 |
|---|---|
| 기체 | B02에서 확인한 동일 기체의 이력으로 연결합니다. 같은 모델의 다른 기체 이력으로 충분성을 채우지 않습니다. |
| 증상·대상 | 같은 계통·부품의 관련 현상인지 문맥으로 비교합니다. 표현 차이나 증상의 정도 차이는 허용하지만 같은 ATA 또는 단일 키워드만으로 연결하지 않습니다. |
| 위치·발생 조건 | 기록된 정보는 비교하되 완전 일치를 요구하지 않습니다. 누락 자체로 자동 탈락시키지 않으며, 부서 제안을 뒷받침하는 나머지 근거를 사용합니다. |
| ATA·JASC | 과거 이력의 실제 값을 보조 근거로 사용합니다. ATA 2자리와 JASC 4자리를 구분합니다. 현재 요청에 없는 JASC를 확인된 사실처럼 생성하거나, 코드 일치만으로 충분하다고 판단하지 않습니다. |
| 담당 부서 | 연결 이력의 담당 부서와 B03의 현재 담당 범위를 함께 확인합니다. 증상·대상 연결 없이 ATA 매핑만으로 직접 배정하지 않습니다. |
| 충분성 | 관련 동일 기체 이력과 부서 연결을 설명할 수 있으면 True로 제안합니다. 관련 이력이 없거나, 서로 다른 대상·부서 후보를 해소할 근거가 부족하면 False로 조사 경로에 넘깁니다. |
| 근거 설명 | 실제 연결한 MH 이력과 증상·대상·부서의 관계를 rationale에 적습니다. 조건 누락이나 차이를 무시하고 동일하다고 서술하지 않습니다. |

최근 이력을 우선 참고하되 '최근 30일만 허용', '최소 2건', 유사도 점수 같은 임의의 통과 조건은 도입하지 않습니다. 시나리오의 최근 30일 배치는 시연 데이터의 구성이지 전체 이력의 검색 제한이 아닙니다.

## 목업 시나리오의 기대 분기

아래 내용은 현 단계 기능 검증을 위한 기대값입니다. 실제 도구와 모델을 실행해 통과한 결과는 아닙니다.

| 시나리오 | LLM1 기대 결과 | 근거 해석 |
|---|---|---|
| S01 | True / SYS, MH-001375 연결 | 같은 기체의 객실 냄새와 PACK 관련 이력에서 기계 계통 담당 부서로 연결합니다. 냄새 종류와 위치가 완전히 같다고 주장하지 않습니다. |
| S02 | True / STR, MH-001453 연결 | 같은 기체의 같은 도어 경고를 연결하며 발생 고도의 차이는 허용합니다. |
| S03 | True / AVI, MH-001487 연결 | 같은 기체의 부기장 산소마스크 마이크 이상과 과거 담당 부서를 연결합니다. |
| S04 | True / ENG, MH-001498 연결 | 순항 중 APU 시동 실패를 연결하며 고도·온도·시도 횟수의 차이는 허용합니다. |
| S05 | True / CAB, MH-001482 연결 | 같은 기체의 승무원 손전등 기능 이상과 객실 부서를 연결합니다. 전방과 2번 승무원석이 같은 위치라고 단정하지 않습니다. |
| S06 | True / ENG, MH-001483 연결 | 게이트의 냄새 증상과 과거 APU 오일 오염 조치·담당 부서를 연결합니다. |
| S07~S15 | False → LLM2 | 신규 증상 또는 다른 기체 유사 사례만으로 동일 기체 이력이 충분하다고 판단하지 않습니다. |
| S16~S20 | False → LLM2 | 여러 계통·부서 후보를 조사 단계에 넘깁니다. 이후 LLM2·3의 사람 검토 분기는 담당 모듈의 범위입니다. |
| S21~S22 | False, 관련 이력 연결 안 함 → LLM2 | 같은 ATA여도 착륙장치 접힘과 브레이크 과열, 객실 온도 조절과 PACK 결함 등 대상·현상이 다른 이력은 연결하지 않습니다. |
| S23 | True / FCS, MH-001567·MH-001574 연결 | 같은 기체의 FLAP SYS 1 FAULT 반복 이력과 현재 FCS 담당 범위를 비교합니다. |
| V1~V6 | LLM1 입력 대상 아님 | Backend 접수 검증 시나리오입니다. |

시나리오 번호, 고정 기체번호 또는 이력 ID를 조건으로 정답을 하드코딩하지 않습니다. 위 사례는 증상·이력·부서 정보를 비교하는 일반 규칙의 검증에 사용합니다. 부서만 맞았는지뿐 아니라 충분성 분기와 실제 연결 이력도 함께 확인합니다.

## 계약상 유지할 경계

- business-mcp의 B01/B02/B03을 사용합니다. DB에 직접 접근하거나 업무 상태·배정을 변경하지 않습니다.
- 실제 B02에서 받은 이력 ID를 linked_history_ids로 보존합니다. 충분한 경우 proposed_department가 필요합니다.
- Classification의 ata_chapter, linked_history_ids, sufficient, proposed_department, rationale 필드를 유지합니다.
- AI 실행기가 근거·부서를 검증한 후 RabbitMQ 이벤트를 보내고 Spring이 실제 배정합니다.
- 목업 기준의 완화는 요청 권한·컨텍스트·근거 검증의 완화를 뜻하지 않습니다. 도구 장애·권한 오류를 이력 없음이나 정상적인 False 판단으로 숨기지 않습니다. 구체적인 오류 전달 계약은 구현 전에 맞춥니다.
- closed_at의 존재만으로 조치 성공을, 부재만으로 미해결 상태를 추정하지 않습니다.

## 후속 프로젝트에서 보강할 것

- 실제 정비 전문가 검토를 통한 세부 부위·위치·발생 조건의 허용 범위와 상충 기준.
- 반복 결함의 기간·횟수·운항 노출량 기준 및 조치 효과 확인.
- 목업과 구분된 실제 데이터의 정확성·원본 추적·부서 라벨 검증.
- 중복 문장과 부서 편중을 고려한 독립 평가 데이터와 운영 성능 평가.

현재 목업 시나리오의 통과는 서비스 흐름 검증으로 보고합니다. 실제 항공사 데이터에서의 분류 정확도나 정비 판단 검증으로 확대해서 보고하지 않습니다.
