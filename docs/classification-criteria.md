# LLM1 분류 기준

확정: 2026-10-21, 사용자 합의. 현재 목업 기반 기능 검증의 분류 기준은 이 문서로 고정합니다. 변경은 사용자와 다시 합의하며, 후속 보강 항목을 현재 필수 조건으로 추가하지 않습니다. 팀 코드 검토 후 사용자 지시로 LLM1과 FastAPI 서버를 구현했습니다.

2026-10-23 사용자 요청으로 맥락 비교와 LLM1·2·3 역할 분리를 보강했습니다.
기존 충분성 원칙과 직접 배정 경로는 유지하며, 공통 문자열 필수 조건을 제거하고
대상·현상·부정·상충 비교 및 각각의 원문 인용 검증을 사용합니다.
LLM2는 LLM1 판단을 받지 않고 독립 조사하며, LLM3가 두 판단과 근거를 비교합니다.
구현과 검증 범위는 [판단 분리 설계](contextual-handoff.md)를 따릅니다.

## 현재 목적과 기준 데이터

사용자 결정에 따라 현재 Backend 목업과 테스트 시나리오를 서비스 흐름 검증의 기준으로 사용합니다. 이 데이터 양식에서 확인 가능한 정보로 이력 연결과 담당 부서 제안을 판단합니다. 더 엄격한 항공 정비 기준, 상세 위치·발생 조건의 일치 기준, 운영 성능 검증은 후속 프로젝트에서 보강합니다.

현재 데이터 기준은 Backend `34a452946833e840120216a9c6fa6aca45d02f6e`의 서비스 평가셋과 수리이력 v2입니다. 데이터셋 변경은 아래 판단 원칙을 자동으로 변경하지 않습니다.

| 자료 | 현재 기준 | 용도 |
| --- | --- | --- |
| [서비스 시나리오](https://github.com/mro-agent-proj/backend/blob/34a452946833e840120216a9c6fa6aca45d02f6e/data/eval/service/scenarios.jsonl) | 200건 (`SV-*`) | 실제 서비스 경로 평가 |
| [정비 이력 시드](https://github.com/mro-agent-proj/backend/blob/34a452946833e840120216a9c6fa6aca45d02f6e/data/seed/maintenance_history_v2.csv) | 1,600건 | 시나리오와 짝을 이루는 업무 이력 |
| [부서 시드](https://github.com/mro-agent-proj/backend/blob/34a452946833e840120216a9c6fa6aca45d02f6e/data/seed/departments.csv) | 8개 부서 | 부서 코드·담당 ATA |
| [접수 검증](https://github.com/mro-agent-proj/backend/blob/34a452946833e840120216a9c6fa6aca45d02f6e/data/eval/scenario/validation.jsonl) | 6건 (`V1`~`V6`) | AI 작업 생성 전 Backend 입력 검증 |

수리이력 CSV의 컬럼은 `id`, `tail_number`, `reported_at`, `symptom_text`, `ata_chapter`, `jasc_code`, `action_taken`, `department_code`, `closed_at`입니다. 발생 단계·고도·온도·부위·위치는 증상 문장에 일부 포함되며, 이 CSV에는 원본 SDR 행 ID 컬럼이 없습니다.

실시간 판단 근거는 business-mcp가 반환한 요청·동일 기체 이력·부서 정보입니다. 평가 메타데이터인 `expected`, `source`, `label_check`는 접수에 보내지 않고 기체번호·항공사·기종·증상 4개 필드만 보냅니다. 기존 DB는 CSV 교체만으로 갱신되지 않으므로 평가 전 Backend 담당 절차에 따라 이력 버전을 확인합니다.

이전 평가셋은 현재 평가 대상에서 제외했습니다. 당시 데이터·기대 분기·실행 성적은 [과거 기록](archive/legacy-scenarios-2026-10-21.md)에 보존하며, 과거 MH ID를 현재 v2 이력에 그대로 대입하지 않습니다.

## 사용자와 합의한 기본 방향

**같은 기체의 증상·발생 조건과 담당 부서 연결 근거가 충분하면, LLM2 추가 조사 없이 담당 부서 배정을 제안할 수 있습니다.**

현 단계에서 충분성은 목업이 제공하는 정보 수준으로 판단합니다. 표현·세부 위치·발생 조건이 완전히 같아야 한다는 조건은 두지 않습니다. 조건이 누락되거나 일부 달라도, 관찰된 증상과 대상 계통·부품 및 과거 담당 부서가 현재 부서 담당 범위로 연결되면 허용합니다. 확인되지 않은 조건을 같다고 추정해 채우지는 않습니다.

과거 조치 내용과 그 결과의 확인은 모든 부서 제안의 필수 조건이 아닙니다. 제공된 조치·결과는 대상 계통과 부서 연결을 설명하는 보강 정보로 사용합니다. 충분성은 담당 부서를 제안할 근거에 대한 판단이며 정비 방법이나 운항 가능 여부를 결정하지 않습니다.

## 확정한 판단 기준

| 항목 | 현재 적용할 기준 |
|---|---|
| 기체 | B02에서 확인한 동일 기체의 이력으로 연결합니다. 같은 모델의 다른 기체 이력으로 충분성을 채우지 않습니다. |
| 증상·대상 | 같은 계통·부품의 관련 현상인지 문맥으로 비교합니다. 표현 차이나 증상의 정도 차이는 허용하지만 같은 ATA 또는 단일 키워드만으로 연결하지 않습니다. |
| 위치·발생 조건 | 기록된 정보는 비교하되 완전 일치를 요구하지 않습니다. 누락 자체로 자동 탈락시키지 않으며, 부서 제안을 뒷받침하는 나머지 근거를 사용합니다. |
| ATA·JASC | 과거 이력의 실제 값을 보조 근거로 사용합니다. ATA 2자리와 JASC 4자리를 구분합니다. 현재 요청에 없는 JASC를 확인된 사실처럼 생성하거나, 코드 일치만으로 충분하다고 판단하지 않습니다. |
| 담당 부서 | 연결 이력의 담당 부서와 B03의 현재 담당 범위를 함께 확인합니다. 증상·대상 연결 없이 ATA 매핑만으로 직접 배정하지 않습니다. |
| 충분성 | 관련 동일 기체 이력과 부서 연결을 설명할 수 있으면 True로 제안합니다. 관련 이력이 없거나, 서로 다른 대상·부서 후보를 해소할 근거가 부족하면 False로 조사 경로에 넘깁니다. |
| 근거 설명 | 실제 연결한 MH 이력과 증상·대상·부서의 관계를 rationale에 적습니다. 조건 누락이나 차이를 무시하고 동일하다고 서술하지 않습니다. |

최근 이력을 우선 참고하되 '최근 30일만 허용', '최소 2건', 유사도 점수 같은 임의의 통과 조건은 도입하지 않습니다. 시드 데이터의 날짜 분포를 전체 이력의 검색 제한으로 사용하지 않습니다.

## 현재 평가에서 확인할 것

서비스 시나리오의 기대 상태·허용 부서·금지 이력은 평가기에만 둡니다. 시나리오 번호, 고정 기체번호 또는 이력 ID로 정답을 하드코딩하지 않습니다. 부서 일치뿐 아니라 충분성 분기, 실제 연결 이력, 현재 증상과의 의미적 대응을 함께 확인합니다. 접수 검증 사례는 LLM1 입력 대상이 아닙니다.

## 계약상 유지할 경계

- business-mcp의 B01/B02/B03을 사용합니다. DB에 직접 접근하거나 업무 상태·배정을 변경하지 않습니다.
- 실제 B02에서 받은 이력 ID를 linked_history_ids로 보존합니다. 충분한 경우 proposed_department가 필요합니다.
- Classification의 ata_chapter, linked_history_ids, sufficient, proposed_department, rationale 필드를 유지합니다.
- AI 실행기가 근거·부서를 검증한 후 RabbitMQ 이벤트를 보내고 Spring이 실제 배정합니다.
- 목업 기준의 완화는 요청 권한·컨텍스트·근거 검증의 완화를 뜻하지 않습니다. 도구 장애·권한 오류를 이력 없음이나 정상적인 False 판단으로 숨기지 않습니다. 구체적인 오류 전달 계약은 구현 전에 맞춥니다.
- closed_at의 존재만으로 조치 성공을, 부재만으로 미해결 상태를 추정하지 않습니다.

## 후속 프로젝트에서 보강할 것

- 실제 정비 전문가 검토를 통한 세부 부위·위치·발생 조건의 허용 범위와 상충 기준.
- 반복 결함의 기간·횟수·운항 노출량 기준 및 조치 효과 확인.
- 목업과 구분된 실제 데이터의 정확성·원본 추적·부서 라벨 검증.
- 중복 문장과 부서 편중을 고려한 독립 평가 데이터와 운영 성능 평가.

현재 목업 시나리오의 통과는 서비스 흐름 검증으로 보고합니다. 실제 항공사 데이터에서의 분류 정확도나 정비 판단 검증으로 확대해서 보고하지 않습니다.
